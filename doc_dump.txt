FAMILY SOCIAL NETWORK
PHASE 1 — CORE FAMILY NETWORK

Complete Phase 1 implementation specification — divided into 5 stages

1. Phase 1 Purpose

Phase 1 is the complete core family-network foundation of the project. Its purpose is to allow users to create profiles, establish and verify family relationships, handle conflicting relationship claims, represent relatives who do not yet have accounts, build a relationship graph, explore that graph through an interactive family tree, calculate how two connected people are related, and highlight the relationship path between them.

Phase 1 must work as a complete standalone family relationship system. It does not depend on later features.

STAGE 1 — AUTHENTICATION & USER PROFILES

Stage 1 creates the identity and profile foundation required before users can build family relationships.

5. Stage 1 Objectives

Allow a person to create an account.

Allow a registered user to log in securely.

Maintain the user's account state.

Create a family-oriented user profile.

Store profile information separately from relationship records.

Prepare the user identity that will later become a node in the family graph.

6. Authentication

User registration

User login

JWT-based authentication

Protected routes

Logout/session handling

Password security using appropriate password hashing

Authentication middleware on protected backend routes

7. User Profile Fields

Caste/subcaste must remain optional and private by default. Region of origin, mother tongue, surname information, and caste/subcaste are profile information only. They must not be used as automatic proof that two people are relatives.

8. Stage 1 User Flow

User opens the registration page.

User creates an account.

System validates the registration data.

System creates the user account.

User logs in.

System creates/authenticates the user session using JWT.

User completes or edits their profile.

Profile becomes available for the family-network system.

The user can proceed to adding family relationships.

STAGE 2 — RELATIONSHIP REQUESTS & VERIFICATION

Stage 2 introduces the actual family relationship system. Users can connect to other accounts by explicitly selecting a supported family relationship.

11. Stage 2 Objectives

Allow a user to search for another person.

Allow the user to select a relationship type.

Send a relationship request.

Allow the recipient to accept or reject the request.

Track relationship status.

Allow accepted relationships to become verified within the platform.

Create the relationship edge only according to the application's defined relationship rules and status.

12. Supported Relationship Types

The application should use explicit relationship records and defined inverse mappings rather than assuming relationships from unrelated profile attributes.

15. Relationship Verification

Verification is platform-level confirmation of the relationship record. It is not legal identity verification or legal proof of a family relationship.

The system should keep relationship status explicit so the family graph does not treat every unconfirmed claim as equally established.

STAGE 3 — DUMMY PROFILES & CONFLICT HANDLING

Stage 3 solves two important real-world family-network problems: relatives who do not yet have accounts and conflicting relationship claims.

19. Dummy Relative Profiles

A user can create a dummy profile when a relative does not have an account on the platform. The dummy profile exists to represent the relative in the family network and family tree.

20. Dummy Profile Information

Internal platform ID

Name

Basic information required by the application

Dummy/account state

Relationship connections

21. Dummy Profile Restrictions

A dummy profile cannot post.

A dummy profile cannot function as an active social account.

A dummy profile cannot independently join or create social groups.

The dummy profile exists for family relationship and tree purposes until it is claimed.

22. Claim Dummy Profile

When the real person later creates or claims the profile, the existing dummy profile can be converted into a real account while retaining the established family relationships.

Dummy Relative
      ↓
Real Person Claims Profile
      ↓
Account Becomes Active
      ↓
Existing Family Relationships Remain Connected

23. Dummy Profile Data Model

DummyProfile / User Account State
├── id
├── name
├── accountType = DUMMY / REAL
├── basicProfileData
└── claimState

A separate permanent dummy-profile table is optional at implementation level if the User model can safely represent the account state. The important requirement is that the profile has a stable internal ID and can later be claimed.

24. Relationship Conflict Handling

The platform must not silently replace an existing family relationship when another conflicting claim is submitted.

Existing:
Phani → Father → Ramesh

New claim:
Phani → Father → Suresh

System result:
Keep the existing relationship record.
Create/track the new claim as disputed or pending according to the defined workflow.

25. Conflict States

Pending

Accepted

Rejected

Disputed

26. Conflict Handling Flow

User submits a relationship claim.

System checks existing relationship records relevant to the relationship type.

If no conflict exists, the request follows the normal relationship flow.

If a conflicting relationship exists, the system does not silently overwrite it.

The new claim is marked as disputed/pending according to the application workflow.

The relevant users can see the relationship status.

The final graph should use the application's defined accepted/verified relationship rules.

27. Stage 3 Completion Criteria

A user can create a dummy relative.

The dummy relative appears in the family relationship network.

Dummy profiles cannot behave as active social accounts.

A real person can claim the dummy profile.

Existing relationships remain connected after a successful claim.

Conflicting relationship claims are detected.

Conflicting claims are not silently used to overwrite existing data.

Relationship records clearly show their status.

STAGE 4 — FAMILY GRAPH & INTERACTIVE FAMILY TREE

Stage 4 turns the relationship records into the central family graph and provides the interactive family-tree experience.

28. Stage 4 Objectives

Represent users and relatives as graph nodes.

Represent family relationships as graph edges.

Generate the family tree from relationship data.

Allow users to explore family branches.

Open a person's profile from the tree.

Show relationship labels.

Show relationship status information.

Represent dummy profiles.

Support the relationship path functionality required in Stage 5.

29. Family Graph Model

Users = Nodes
Relationships = Edges

Example:
Phani → Father → Ramesh
Phani → Mother → Sunita
Ramesh → Father → Mohan
Sunita → Brother → Raj
Raj → Son → Rahul

30. Why the Tree Is Derived

The application should not maintain a separate rigid family-tree structure with fields such as fatherId, motherId, uncleId, brotherId and sisterId. The relationship graph is the source of truth. The interactive family tree is generated from the graph.

STAGE 5 — HOW ARE WE RELATED? & RELATIONSHIP PATH HIGHLIGHTING

Stage 5 completes the Phase 1 family-network experience. It uses graph traversal to calculate the connection between two people and then visually highlights that connection in the family tree.

36. Stage 5 Objectives

Find a path between two connected people.

Translate the path into understandable relationship steps.

Display the resulting relationship information.

Open the relationship path from a person's profile.

Highlight the exact path in the interactive family tree.

37. How Are We Related?

The system uses the family relationship graph to find a path between the current user and another connected person.

Example:
Phani
  ↓
Mother
  ↓
Mother's Brother
  ↓
Brother's Son
  ↓
Rahul

Relationship result:
Rahul is Phani's cousin.

38. Graph Traversal

A graph traversal algorithm such as Breadth-First Search (BFS) can be used to find a path between two nodes. The stored relationship edges provide the actual evidence for the path.

Start Node = Current User
Target Node = Selected Relative

BFS / graph traversal
        ↓
Find connected path
        ↓
Convert edges into relationship steps
        ↓
Display relationship explanation

39. Relationship Path Highlighting

When a user selects 'View Relationship in Family Tree', the system opens the tree and highlights the nodes and edges that form the relationship path.

Example:

YOU
 │
 ▼
FATHER
 │
 ▼
FATHER'S BROTHER
 │
 ▼
COUSIN

Only the relevant path is highlighted in the tree.

40. Stage 5 User Flow

User opens another connected person's profile.

The system identifies the known relationship information.

User selects 'How Are We Related?' or 'View Relationship in Family Tree'.

Backend finds a valid graph path between the two people.

Backend returns the relationship nodes/edges in order.

Frontend opens the family tree at the relevant area.

The path nodes and edges are highlighted.

The relationship explanation is displayed alongside the tree.

50. Phase 1 Security and Data Rules

Passwords must not be stored as plain text.

Protected endpoints must require authentication.

A user must not be able to edit another user's profile without an authorized workflow.

Relationship changes must validate that the requester is allowed to perform the action.

Relationship conflicts must not silently overwrite existing records.

Sensitive profile information such as optional caste/subcaste must have controlled visibility.

Government identity numbers such as Aadhaar are not part of the Phase 1 data model.

Family relationship information should be exposed only according to the defined access/visibility rules.
